# Open Interpreter Runtime Migration — Stage 3 Sandbox Backend Design

## Status

Continuation of the approved Local_AI_Agent Open Interpreter migration. Stage 1 introduced the service/backend boundary. Stage 2 added the managed Rust Open Interpreter Host backend. Stage 3 migrates Sandbox mode while preserving the existing Docker security boundary and legacy fallback.

## Goal

Run Open Interpreter 0.0.38 App Server inside the existing hardened Local_AI_Agent Docker Sandbox without weakening Docker privileges, while preserving folder policy, CPU/RAM limits, WARP/Tor/block modes, SearXNG/PreTool access, persistent state, approvals, and the old custom REPL as rollback fallback.

## Security decision

Open Interpreter's inner Linux sandbox uses mechanisms that may not be available inside an already-restricted Docker container. Local_AI_Agent will **not** add `--privileged`, `CAP_SYS_ADMIN`, `seccomp=unconfined`, host PID/network namespaces, or equivalent relaxations merely to make nested sandboxing work.

The Docker container remains the mandatory outer isolation boundary. Inside that container, Open Interpreter uses:

```text
approvalPolicy = on-request
approvalsReviewer = user
sandbox = danger-full-access
```

`danger-full-access` is therefore valid **only in the Sandbox backend**. Host mode remains `workspace-write` and must never inherit this value.

The container still physically limits the process to mounted paths, tmpfs masks, configured network path, memory, and CPUs.

## Chosen integration approach

Three approaches were considered:

1. Rebuild a second Docker command generator for App Server.
2. Refactor the legacy Docker builder into a common structured builder in the same migration.
3. Reuse the existing legacy Sandbox command as the security-policy source and transform only the image command tail.

Stage 3 uses **approach 3**. It minimizes security-policy drift and keeps Stage 3 reversible. The current `build_sandbox_pipe_cmd()` continues to generate the exact Docker options for mounts, masks, proxy/block mode, resource limits, state mounts, and environment. `SandboxOpenInterpreterBackend` consumes the generated command from `AgentConfig.legacy_runtime`, removes only legacy-REPL-specific environment payloads, and replaces the executable tail with Open Interpreter App Server.

A later cleanup stage may refactor common Docker policy construction after both runtimes have passed parity tests.

## Docker image

The `llm-agent-sandbox` image moves from Python `pip install open-interpreter` to the pinned standalone Rust Open Interpreter 0.0.38 installer.

The Dockerfile keeps the current Python 3.11 runtime and developer utilities because Local_AI_Agent's PreTool modules and user Python code depend on them.

The image installs the official pinned script:

```text
https://raw.githubusercontent.com/openinterpreter/openinterpreter/
rust-v0.0.38/scripts/install/install.sh
```

with:

```text
OPEN_INTERPRETER_RELEASE=0.0.38
OPEN_INTERPRETER_NONINTERACTIVE=1
OPEN_INTERPRETER_INSTALL_DIR=/home/agent/.local/bin
INTERPRETER_HOME=/home/agent/.openinterpreter-package
```

The image carries labels:

```text
local-ai-agent.runtime=app-server
local-ai-agent.open-interpreter-version=0.0.38
```

The installer no longer treats image existence alone as sufficient. It skips rebuilding only when both labels match. An older unlabelled/Python-OI image is rebuilt automatically.

## Sandbox backend

New module:

```text
launcher/agent/sandbox_backend.py
```

Main type:

```python
class SandboxOpenInterpreterBackend(OpenInterpreterBackend): ...
```

It reuses App Server transport, turn/session handling, approval handling, and normalized events from Stage 2.

It overrides only runtime availability, process command/environment construction, and thread sandbox mode.

### Availability

The managed Sandbox backend is available when Docker image inspection reports both required labels. If Docker is unavailable, the image is missing, or labels do not match, backend selection returns `LegacyBackend`.

This preserves compatibility with existing installations until INSTALL rebuilds the image.

## Docker command transformation

Input is the current `LegacyRuntimeSpec.command`, generated by `build_sandbox_pipe_cmd()` and already adjusted by `agent_chat.py` for runtime networking, system-message file, PreTool, and shared network.

The transform:

1. Requires the command to begin with `docker run` and contain the configured Sandbox image.
2. Copies all Docker options before the image token.
3. Removes only legacy custom-REPL environment pairs whose values begin with:
   - `AGENT_REPL_SRC=`
   - `AGENT_MODEL_LADDER=`
   - `LITELLM_LOG=`
4. Preserves:
   - workspace mount
   - persistent state mount
   - allowed folder mounts
   - denied-folder tmpfs masks
   - `--dns=0.0.0.0` block mode
   - WARP/Tor proxy environment
   - `--network llm_net`
   - CPU/memory constraints
   - no-display/vision guards
   - `PYTHONPATH=/home/agent/.agent_state`
   - all Local_AI_Agent settings environment already injected into the command
5. Adds/overrides:

```text
INTERPRETER_HOME=/home/agent/.agent_state/open_interpreter
CODEX_OSS_BASE_URL=http://host.docker.internal:11434/v1
NO_PROXY=host.docker.internal,localhost,127.0.0.1,::1,llm_searxng
no_proxy=host.docker.internal,localhost,127.0.0.1,::1,llm_searxng
SEARXNG_URL=http://llm_searxng:8080
PYTHONPATH=/home/agent/.agent_state
```

6. Replaces the image command tail with:

```text
interpreter
-c check_for_update_on_startup=false
-c web_search="disabled"
app-server --listen stdio://
```

The built-in Open Interpreter web search is disabled so it cannot bypass Local_AI_Agent's selected network/search policy.

## Ollama connectivity

Inside Docker, the built-in `ollama` provider points to:

```text
http://host.docker.internal:11434/v1
```

The existing `--add-host=host.docker.internal:host-gateway` remains intact.

`host.docker.internal` is explicitly included in `NO_PROXY`, ensuring local model traffic does not traverse WARP/Tor.

## SearXNG and PreTool preservation

The existing `agent_chat.py` PreTool mirror runs before backend start and remains unchanged. The state mount exposes the mirror as:

```text
/home/agent/.agent_state/PreTool
```

`PYTHONPATH=/home/agent/.agent_state` keeps imports such as:

```python
from PreTool.search import web_search, research
```

working for Python executed by Open Interpreter.

Structured Sandbox developer instructions explicitly state:

- Open Interpreter built-in web search is disabled.
- For current external information, use `PreTool.search.web_search`, `search_summary`, or `research`.
- SearXNG is the preferred local search path.
- Do not send private local content as external search queries.

The current SearXNG autostart and Docker network connection logic in `agent_chat.py` remains the runtime owner of `llm_searxng`.

## Shared structured instructions

Stage 2 exposed a regression risk: legacy Host/Sandbox builders append a privacy clause, whereas structured Host currently receives only `profile.system_message`.

Stage 3 introduces:

```text
launcher/agent/instructions.py
```

with:

```python
build_structured_instructions(profile_message, *, sandbox: bool) -> str
```

It appends the existing privacy requirements for both Host and Sandbox. Sandbox additionally receives Docker/PreTool/search guidance.

`agent_chat.py` uses this helper when creating `AgentConfig.instructions`.

The legacy builders remain unchanged and continue using their current embedded privacy clause.

## Thread configuration

Host remains:

```text
sandbox=workspace-write
```

Sandbox backend overrides only this field to:

```text
sandbox=danger-full-access
```

Other structured thread fields remain:

```text
model=<selected Ollama model>
modelProvider=ollama
approvalPolicy=on-request
approvalsReviewer=user
serviceName=Local_AI_Agent
developerInstructions=<structured instructions>
```

The App Server process `cwd` is `/home/agent/workspace` inside the container, while the host-side `AgentConfig.workspace` remains the selected host workspace. `SandboxOpenInterpreterBackend` therefore overrides the thread `cwd` sent to App Server.

## Backend factory

`create_backend(mode, env)` becomes:

```text
host:
  managed interpreter.exe exists -> OpenInterpreterBackend
  otherwise -> LegacyBackend

sandbox:
  labelled App Server image exists -> SandboxOpenInterpreterBackend
  otherwise -> LegacyBackend
```

No automatic image rebuild is triggered at chat launch. INSTALL / Docker image rebuild remains responsible for building images.

## Lifecycle

The App Server subprocess visible to the launcher is the `docker run` CLI process. Normal `AppServerClient.stop()` terminates that process, but Docker cleanup must remain explicit to prevent orphan containers.

`SandboxOpenInterpreterBackend.stop()` therefore additionally uses the container name already present in the Docker command and performs the same best-effort:

```text
docker stop -t 2 <name>
docker rm -f <name>
```

No new broad orphan-cleanup patterns are introduced; existing global cleanup remains a secondary safety net.

Restart receives a newly rebuilt legacy policy command from `agent_chat.py`, so rotating container names and folder-policy remount behavior remain intact.

## GUI behavior

The existing Stage 2 normalized event and approval UI is reused.

The Stop button keeps existing Sandbox semantics: it stops the current container/backend, rather than merely interrupting a turn. Host managed mode continues to use `turn/interrupt` first.

`/session` and `/resume` work for both structured Host and structured Sandbox.

`/model` stops and restarts the Sandbox container with the selected model, preserving current behavior.

## Legacy removal policy

Stage 3 does **not** delete:

- `_AGENT_REPL_SRC_B64`
- `_AGENT_REPL_BOOTSTRAP`
- `build_sandbox_pipe_cmd`
- `UnifiedAgent`
- the old Python Host venv

They remain fallback paths until parity verification is complete.

## Tests

Add or update tests for:

1. structured instruction privacy clause and Sandbox search guidance
2. Docker command transform exact preservation of mounts/tmpfs/network/resource flags
3. legacy REPL env removal
4. App Server tail and local Ollama env
5. Sandbox thread `danger-full-access` while Host remains `workspace-write`
6. explicit Docker stop/rm cleanup
7. image label detection and factory fallback
8. Dockerfile pinned 0.0.38 standalone installer
9. installer rebuild decision on missing/wrong labels
10. boundary guard that no `--privileged`, `CAP_SYS_ADMIN`, `seccomp=unconfined`, or host namespace relaxation is added
11. full existing Stage 1/2 tests unchanged except intentional shared instruction expectations

## Acceptance gate

Stage 3 is ready for default structured Sandbox only when Windows/Docker verification demonstrates:

- managed image label is 0.0.38/app-server
- App Server initializes inside current Docker flags
- Ollama responds through host.docker.internal without proxying
- selected workspace read/write works
- unmounted host paths remain inaccessible
- allowed mounts work
- denied tmpfs-masked paths remain hidden
- block mode has no external internet
- WARP and Tor modes route PreTool search as before
- SearXNG remains reachable through the selected Docker network
- command/file approvals can accept and decline
- Stop/restart leaves no Sandbox container
- CPU/RAM limits remain present
- no Docker privilege relaxation is present

If Open Interpreter `workspace-write` inside Docker later becomes viable under the exact same outer flags, it may replace the inner `danger-full-access`; this is an optional hardening improvement, not a reason to weaken Docker.
